## 风险与注意事项

- `main` 是干净稳定的封版基线，M13-M18 在 `feat/ai-agent` 分支开发，不逐模块 push。
- M13-M18 **已完成并本地提交**（领先 origin 14 个提交）；按策略在系统冻结检查点统一 push，需用户单独确认，最后一次性合并回 `main`。
- 仓库旧文档里存在历史阶段的“M2 数据一致性”，它不是毕业设计当前 M2，不要混用。
- 后续描述项目能力时必须区分“已实现”和“规划中”，不得虚构评估数据、性能或效果。
- 推荐指标（`HitRate@10` = 0.8889）来自**合成数据 + 留一法**，测试集仅 9 位用户；
  引用时必须一并说明局限（见 `ai-agent-upgrade/m17-eval-report.md` 的「局限与诚实声明」）。
- 全量 `mvn test` 会清空 Redis 向量索引 `bitforum-kb`（M15 起的既有行为），
  跑完后用 `M17_VECTOR_PROBE=true -Dtest=RecommendVectorRecallProbe` 重建。
- `ai_execution_trace` / `ai_usage_stat` 会随 AI 调用量增长，当前没有归档或清理策略（长期需要）。
- AI 相关排错先看**执行轨迹页**（`/admin/ai-traces`）：路由、工具调用链、每步耗时、
  token 与降级原因都在那里，比翻日志快。
- 不要删除或回滚 `docs/graduation/m1-category/`。
- 不要修改历史 Flyway 脚本 `V1` 至 `V12`，后续数据库变化继续新增后续迁移（AI 模块从 `V13` 开始）。
- 不要提交 `.env`；大模型 API Key 只通过环境变量 `DEEPSEEK_API_KEY` 读取。
- Agent 的写操作必须经用户身份透传与二次确认，不豁免现有 `LoginInterceptor` / `AdminInterceptor`。
- AI 调用必须可降级，论坛主流程不得因 AI 故障而阻塞或报错。
- ONNX 嵌入模型加载与 Redis Stack 替换是两个尚未实测的技术点，M13/M15 开始前必须先做最小验证。
