# M17 智能推荐评测规范 v1（冻结）

> **本文件是"球门"，不是"射门结果"。** 先把它冻结，再跑数据 —— 沿用 M16 的做法。
>
> 冻结时间：2026-09-19。冻结时的实现状态见 `progress.md` 的 M17 记录。
> 与 M16 规范的差别：M16 要确定的是一个**阈值**；M17 的排序算法（RRF）不需要调参，
> 因此本规范的重点从"阈值怎么定"移到**Ground Truth 怎么构造**。

## 一、为什么要冻结

M16 的经历值得原样搬过来：当时用开发集扫出来的自动放行阈值看起来很漂亮（正常内容覆盖 13.3%），
拿到独立测试集上覆盖率直接掉到 **0%** —— 阈值过拟合了开发集那 4 条高置信样本。
如果 M17 也是"先跑数字、再回头解释"，很可能重演同一件事：
数字好看就说算法好，数字难看就换口径。

因此本轮先固定三件事：**Ground Truth 怎么来、指标怎么算、基线是什么**，
之后只允许按规范执行，不允许用测试集结果反过来改口径。

## 二、推荐任务与信号定义

**任务**：给定用户（可能未登录）与可选的一篇来源文章，输出一个有序的文章列表。

**召回通道**（三路，定义必须固定）：

| 通道 | 数据来源 | 语义 |
| --- | --- | --- |
| `vector` | M15 的 Redis 向量索引 `bitforum-kb`（bge-base-zh-v1.5，768 维） | 内容与来源文章相似 |
| `hot` | M6 的热榜 ZSet `article:hot` | 近期热度（浏览 +1、点赞 +3 累积） |
| `follow` | M9 的 `user_follow` 表 | 来自当前用户关注的作者 |

**融合方式**：RRF（Reciprocal Rank Fusion），`score = Σ 1/(k + rank)`，**k 固定为 60**。
选它而不是加权求和的原因见 `RecommendFusionService` 的类注释：三路分数不可比，
而归一化与权重都需要数据才能定 —— 当前数据不足以支撑这种"拍参数"。

**排序完全由 Java 完成，LLM 不参与选文**：模型只生成"为什么推荐"的解释。
理由是排序之上的说明，不是排序的一部分。这条决定了下面的指标定义里**不含任何模型输出**。

## 三、Ground Truth：留一法（leave-one-out）

### 3.1 一个必须先解决的自相矛盾

M17 的产品策略是「候选过滤只排除作者本人与已收藏文章」。
如果直接拿"用户收藏过的文章"当命中目标，那么这些文章**永远不可能出现在推荐里**，
命中率恒为 0 —— 评测会得出"系统完全无效"的荒谬结论。

解决办法就是留一法：**把要预测的那一篇从"已收藏"里拿出来，当作"用户下一步会收藏的文章"**。
模型/算法看不到它，评测时才拿它核对。

### 3.2 严格定义

对每个参与评测的用户 `u`：

1. 取其收藏集合 `F(u)`（按 `article_favorite.create_time` 升序）；
2. **目标文章 `t`**：从 `F(u)` 中随机抽取一篇（随机种子固定，保证可复现）。
   - 约束：`t` 必须当前仍是 `PUBLISHED`；否则换一篇，换不到则该用户不参与；
   - 约束：`|F(u)| ≥ 3` 才参与评测 —— 只留一篇出来会让"已知偏好"几乎为空，
     系统拿不到足够信号，测的就不是算法而是运气；
3. **排除集**（模拟"该用户此刻已经看过这些"）：
   - `F(u) \ {t}`（除目标外的收藏）；
   - `u` 自己发布的文章；
   - **注意：`t` 不在排除集里**；
   - 浏览过的不排除（与产品策略一致）；
4. **推荐**：在"CandidatePool = 全部已发布文章 − 排除集"上跑融合推荐，取 Top-10；
5. **命中判定**：`t` 是否出现在这 Top-10 中，以及排在第几位。

### 3.3 为什么不用"时间切分"

更严格的离线评测会按时间切分（用 T 时刻之前的行为预测 T 之后的行为）。
本项目的行为数据是**合成**的，时间戳不具备真实因果含义，
按时间切分只会增加一层"看起来严谨"的假象。留一法在合成数据上是诚实且可解释的选择。

## 四、指标公式

设参与评测的用户数为 `N`，用户 `i` 的目标文章在推荐列表中的排名为 `rank_i`
（未出现在 Top-10 中则记 `rank_i = ∞`，其倒数为 0）。

| 指标 | 公式 | 回答的问题 |
| --- | --- | --- |
| **HitRate@10** | `(1/N) × |{i : rank_i ≤ 10}|` | 系统**能不能找到**用户会感兴趣的东西 |
| **MRR@10** | `(1/N) × Σ (1 / rank_i)` | 找到了的话**排得够不够靠前** |

**必报的分布**（避免只报总数掩盖结构）：

1. 命中排名的分布（第 1 位命中几个用户、第 2 位几个……）；
2. 每个用户的 Top-10 里各召回通道的覆盖情况（`vector` / `hot` / `follow` 各贡献了几篇）；
3. 参与评测的用户数 `N` 与候选池规模（说明样本量，避免把小数当结论）。

**为什么用 @10**：产品上"相关推荐"一屏展示约 5~10 条，Top-10 是功能真实可用的范围；
同时候选池只有几十篇，更大的 K 会让指标失去区分度。

## 五、基线定义

| 基线 | 定义 | 作用 |
| --- | --- | --- |
| **`hot`（主基线）** | 只走向量库之外的 `hot` 通道，按热榜分值降序取 Top-10 | 计划书要求的对比对象："命中率与纯热榜基线对比" |
| **`random`（sanity check）** | 在**同一候选池**中随机取 10 篇（随机种子固定） | 判断"热榜是不是真的比瞎猜好"；若热榜与随机无差别，说明热度信号在本数据集上无效 |

**基线必须与推荐系统共用三件事**，否则对比失真（已在代码里由 `RecommendService.assemble` 保证）：

1. **同一份排除集** —— 否则基线能推出用户已收藏的文章，凭空多出命中；
2. **同一套"文章当前必须是 PUBLISHED"的校验** —— 通过复用召回层的 HOT 通道实现；
3. **同一套记录与统计方式** —— 只有 `ai_recommend_log.experiment_tag` 不同
   （`RECOMMEND` / `BASELINE_HOT`），评测脚本按批次分组统计。

## 六、数据集边界

### 6.1 数据来源声明（必须如实写进任何报告）

**本评测使用合成数据**：文章、用户与行为均由项目作者构造，**不是**真实社区流量。
任何引用本评测结果的场合都必须带上这句话。

### 6.2 规模与结构

| 项 | 目标 | 说明 |
| --- | --- | --- |
| 文章 | **40~60 篇** | 分属 8~10 个技术主题，每主题 5~8 篇 |
| 文章正文 | **每篇 300~500 字真实技术内容** | 不能用占位句（T11 的教训，见 6.3） |
| 用户 | **20~30 个** | 每个用户有 1~2 个主兴趣主题 |
| 每用户收藏 | **4~8 篇** | 主要落在其兴趣主题内，可含少量跨主题 |
| 关注关系 | 每个用户关注 1~2 位同主题作者 | 让 `follow` 通道有信号 |

### 6.3 数据质量的硬条件（T11 的直接教训）

T11 实测（`findings.md` 6.15）发现：现有 5 篇已发布文章的**正文只有 44~67 字**，
导致"同主题"和"跨主题"的相似度只差 **0.0048**，向量排序接近随机。
**如果新数据也这样，评测出来的任何数字都只是在测噪声。**

因此数据生成后必须先过一道**区分度检验**，达标才允许进入评测：

```
区分度 = 同主题文章对的平均相似度 − 跨主题文章对的平均相似度
```

- **硬条件：区分度 > 0**，且同主题平均相似度应明显高于跨主题（目标 > 0.05）；
- 检验用真实的嵌入模型与向量索引（与线上同一套），不接受"看起来像"的目测；
- **不达标就重做数据，而不是调算法** —— 这条是为了防止"用算法补偿数据的缺失"。

### 6.4 数据集划分

沿用 M16 的纪律：

| 集合 | 划分 | 用途 |
| --- | --- | --- |
| 开发集 | 约 70% 的用户 | 确认实现正确、观察指标量级、确定 `recallTopK` 等参数 |
| **独立测试集** | 约 30% 的用户 | **最终指标只在这里产出；冻结前不得查看其任何输出；只跑一次** |

用户不跨集合（一个用户要么在开发集要么在测试集），避免同一用户的行为同时影响两边。

### 6.5 明确不属于本评测范围

- 真实用户点击/停留时长等隐式反馈（本项目没有采集）；
- 线上 A/B 实验与流量分配；
- "点赞"作为兴趣信号（当前数据结构无法反查，见 `findings.md` 6.16）；
- 冷启动用户（无任何行为）的效果 —— 只测"有行为但目标被隐藏"的情形。

## 七、实验流程

1. **冻结本规范**（本文件）；
2. 生成合成数据，跑**区分度检验**（6.3），不达标就重做；
3. 在**开发集**上跑通全流程，确认指标口径与统计脚本正确，确定 `recallTopK` / `topN` 等参数；
4. **冻结实现**：记录当时的 git commit（参数与代码都不再变动）；
5. **测试集只跑一次**，产出 `HitRate@10` 与 `MRR@10`（融合推荐 / 纯热榜 / 随机三条）；
6. 如实报告，包含：参与用户数、候选池规模、命中排名分布、通道覆盖、以及 6.1 的合成数据声明。

**禁止事项**：

- 用测试集结果调整算法参数或修改本规范的口径；
- 只报告好看的指标而隐去分布与样本量；
- 把合成数据的结果表述为"真实业务效果"。

## 八、硬约束（不达标即视为不合格）

| 编号 | 约束 | 不达标时的处理 |
| --- | --- | --- |
| C1 | 数据区分度 > 0（同主题 vs 跨主题） | **重做数据**，不得用算法补偿 |
| C2 | 融合推荐的 `HitRate@10` 严格高于纯热榜基线 | 如实报告"未达标"，不得调整测试集或口径 |
| C3 | 测试集只运行一次，且在此之前未查看其输出 | 该次评测作废，需重新生成测试集 |
| C4 | 任何报告都带合成数据声明 | 补上声明，否则该报告不得引用 |

> C2 的措辞是"严格高于"而不是"达到某个数值"：本项目没有真实流量，
> 报出一个绝对数值（例如"命中率 62%"）没有外部效度，只有**与基线的相对比较**才有意义。
