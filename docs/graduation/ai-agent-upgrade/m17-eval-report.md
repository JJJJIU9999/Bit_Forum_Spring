# M17 推荐效果评测报告（合成数据）

> 按 `m17-eval-protocol.md` v1 执行。**本报告使用合成数据，不是真实社区流量。**
> 评测时间：2026-09-19。实现冻结凭证：`.dev-logs/m17-eval-freeze.txt`（测试集运行前记录的 sha256）。

---

## 一、结论摘要

| 问题 | 结论 |
| --- | --- |
| 三路召回 + RRF 融合 是否优于纯热榜基线？ | **是**（开发集与独立测试集均严格高于基线，硬条件 C2 达标） |
| 数据是否足以支撑向量通道？ | **勉强够**：区分度 > 0 通过，但强度弱（详见第四节） |
| 能否推断真实流量上的效果？ | **不能**。合成数据 + 强化的关注信号意味着绝对命中率可能被高估（第六节） |
| 过程中是否发现问题？ | **是，两个**，其中一个已修正并改变了结果（第七节） |

**测试集（独立、只跑一次，9 位用户）**：

| 对比线 | HitRate@10 | MRR@10 |
| --- | --- | --- |
| **融合推荐（三路召回 + RRF）** | **0.8889** | **0.3745** |
| 纯热榜基线 | 0.2222 | 0.0926 |
| 随机（sanity check） | 0.3333 | 0.2444 |

**开发集（21 位用户，用于确认实现与口径）**：

| 对比线 | HitRate@10 | MRR@10 |
| --- | --- | --- |
| **融合推荐** | **0.8095** | **0.5330** |
| 纯热榜基线 | 0.2381 | 0.1302 |
| 随机（sanity check） | 0.2857 | 0.0938 |

## 二、评测设置

| 项 | 设置 |
| --- | --- |
| Ground Truth | 留一法：每个用户隐藏一条收藏作为预测目标，其余收藏进排除集（规范 §3.2） |
| 指标 | `HitRate@10`、`MRR@10`（规范 §4） |
| 对比线 | 融合推荐 / 纯热榜（主基线）/ 随机（sanity check） |
| 候选池 | 55 篇已发布文章（其中合成评测语料 50 篇 + 既有的 5 篇测试文章） |
| 数据集划分 | 用户按 id 排序，前 70% 开发集（21 位）、后 30% 独立测试集（9 位） |
| 融合参数 | RRF `k = 60`，每路召回 `topK = 20`，`topN = 10`（**沿用默认值，未做参数扫描**） |
| 参与门槛 | 收藏数 ≥ 3 的用户（低于此值"已知偏好"太稀疏，测的是运气） |

**关于参数未扫描**：候选池只有 55 篇，三路各取 20 已覆盖大部分候选；
且 RRF 按排名计分，对 `topK` 不敏感。因此没有在开发集上做参数搜索 —— 也就没有过拟合开发集的机会。

## 三、结果细节

### 3.1 命中排名分布（融合推荐）

| 数据集 | 分布 | 说明 |
| --- | --- | --- |
| 开发集 | `{1=9, 2=1, 3=3, 4=1, 5=1, 7=1, 10=1}` | 17 次命中里 9 次排在第 1 位 |
| 测试集 | `{1=2, 3=2, 4=1, 5=1, 7=1, 9=1}` | 8 次命中里只有 2 次在第 1 位，因此 MRR 低于开发集 |

测试集的 HitRate 更高但 MRR 更低：命中的 8 位用户里多数目标排在 3~9 位。
9 位用户的样本量下，单个用户的排名变化就会明显影响 MRR（粒度 1/9 ≈ 0.111）。

### 3.2 各召回通道的贡献（Top-10 累计篇次）

| 数据集 | vector | hot | follow |
| --- | --- | --- | --- |
| 开发集 | 193 | 169 | 82 |
| 测试集 | 81 | 70 | 42 |

三路都实际参与，其中内容相似（vector）贡献最多。

> 这一项是**必须报告的**：第一次评测时 vector 的贡献是 **0**，
> 而指标看起来完全正常（HitRate 0.7619）—— 详见第七节问题 1。

## 四、数据质量检验（硬条件 C1）

对 50 篇合成语料做"同主题 vs 跨主题"的相似度检验（用与线上相同的嵌入模型与向量索引）：

| 指标 | 实测 | 参考 |
| --- | --- | --- |
| 同主题文章对平均相似度 | 0.8850（576 对） | |
| 跨主题文章对平均相似度 | 0.8703（4716 对） | |
| **区分度 = 差值** | **0.0147** | 硬条件 > 0 ✅；目标 > 0.05 ❌ |
| **Top-5 中同主题文章占比** | **45.6%** | 随机期望 12.5% ✅ |

**诚实解读**：平均相似度差这个指标只勉强达标（0.0147），
因为 bge 对中文技术段落的相似度整体偏高、都挤在 0.87~0.89 的窄区间里。
但**排序层面**的区分度很强（45.6% 对 12.5%）。

这也说明：在本项目的数据上，相似度的**绝对值**几乎没有意义，**排名**才有意义 ——
这正是融合选用 RRF（按排名计分）而不是加权求和的原因。

## 六、局限与诚实声明（必须与结果一起引用）

1. **数据是合成的**：文章、用户、收藏与关注关系全部由项目作者构造，
   **不是真实社区流量**。任何场合引用本报告都必须带上这句话。
2. **热度与主题无关**：热度用随机值模拟"浏览行为不针对主题"。
   因此纯热榜基线在"主题兴趣"这件事上几乎没有信息量 ——
   随机基线（0.3333 / 0.2857）与热榜（0.2222 / 0.2381）几乎无差别，正说明这一点。
   **所以"融合推荐大幅超越热榜"里有一部分是数据构造的功劳，不能当作算法的真实增益。**
3. **关注信号过强**：合成数据里"用户关注了其兴趣主题的作者"是直接设定的，
   比真实场景中"关注 ≠ 同兴趣"要强得多。这会让 follow 通道的贡献被高估。
4. **测试集样本小**：仅 9 位用户，HitRate 的粒度是 1/9 ≈ 0.111，随机基线一次抽样的波动就很大。
5. **未覆盖的场景**：冷启动用户（无任何行为）、真实点击/停留等隐式反馈、
   时间漂移（用户兴趣变化）、以及线上 A/B 流量验证。
6. **区分度偏弱**：C1 只勉强通过（0.0147 < 目标 0.05），
   向量通道的有效性依赖排序而非分数，对更细粒度的主题区分可能不够。

**一句话**：本评测证明"三路召回 + RRF 融合"在**这套合成数据**上稳定优于纯热榜与随机基线，
但**不能**据此推断真实流量上的效果。

## 七、过程中发现并修正的两个问题

### 问题 1：用户维度的推荐里，向量通道从未被触发（已修正，改变了结果）

第一次开发集评测的通道贡献是 `{hot=160, follow=96}` —— **一个 vector 都没有**，而 HitRate 是 0.7619，
看上去一切正常。原因：向量召回当时只接受"来源文章"（文章详情页场景），
用户维度的推荐没有来源文章，这一路直接返回空。

修正：向量通道支持多查询 —— 来源文章 + 用户最近收藏的若干篇（内容画像）。
修正后开发集 HitRate 从 **0.7619 → 0.8095**，且 vector 成为贡献最大的通道。

> 教训：一个"永远返回空"的通道既不报错、也不让指标变难看，它只是**静默地不参与**。
> 评测报告必须打印通道贡献。

### 问题 2：留一法的泄漏风险（已修正）

留一法把用户的收藏 `t` 当作预测目标。若"兴趣画像"仍把 `t` 算进去，
等于把答案提前告诉算法。修正后 `RecommendService.recommend()` 同时支持外部指定
**排除集**与**兴趣画像**，评测传入的兴趣 = 除目标之外的收藏。

### 问题 3：语料文件在评测后被改写成另一个版本（已对齐，不影响结果）

语料生成过程中，并行的子任务在**测试集运行之后**又改写了一次语料文件
（改写版的正文是 512~1200 字/篇，而数据库里已评测的数据是 329~763 字/篇）。
这会造成一个隐蔽但严重的问题：**仓库里的语料无法复现已评测的那批数据** ——
任何人重跑 `M17EvalDataSeeder` 都会得到与报告不符的数据。

处理：评测完成后，**从数据库反向重建了语料文件**（`M17EvalCorpus.java`），
并逐字校验通过（50/50 篇内容与库中数据完全一致，含末尾换行）。
被冻结的实现代码（`RecommendService` / `RecommendRecallService` / `RecommendFusionService` /
`AiRecommendLog`）的 sha256 **未发生任何变化**，因此本次对齐不触及实现、不影响评测结果的有效性。
更新后的凭证见 `.dev-logs/m17-eval-freeze.txt`（文件中同时记录了这次对齐的原因）。

> 教训：评测的"数据"与"实现"一样需要冻结。只冻结代码、不冻结数据，
> 同样会让一次评测变得不可复现 —— 而且比代码漂移更难发现，因为指标看起来一切正常。

### 7.4 评测之后接入的推荐理由生成（不影响上述结果）

本次评测完成后，M17 接入了 LLM 推荐理由生成（`RecommendReasonAgent`）。
按 M17 实施决策第一条，**排序完全由 Java 完成、LLM 不参与选文**，
因此理由生成只影响展示文案，**不改变召回与排序** —— 本报告的
`HitRate@10` / `MRR@10` 结论仍然成立。

与之相关的唯一变化在推荐记录上：评测时（理由尚未接入）`degraded` 恒为 true，
接入后若理由生成成功则为 false，并会写入 `reason` 字段。
**复跑评测时应设置 `BITFORUM_RECOMMEND_REASON_ENABLED=false`**，
让链路回到与本次评测一致的状态（否则会为每条推荐调用一次模型，白烧额度且拖慢流程）。

## 八、复现方式

> **注意**：本报告执行于推荐理由生成接入**之前**（见 7.4）。复跑时请设置
> `BITFORUM_RECOMMEND_REASON_ENABLED=false`，让链路回到与本次评测一致的状态。

```bash
# 1. 生成合成评测数据（50 篇语料 + 30 位用户 + 收藏/关注/热度，并重建向量索引）
export M17_EVAL_SEED=true
./mvnw -s maven-settings.xml -Dtest=M17EvalDataSeeder test

# 2. 数据区分度检验（硬条件 C1）
export M17_EVAL_CHECK=true
./mvnw -s maven-settings.xml -Dtest=M17CorpusDiscriminationCheck test

# 3. 开发集评测（可反复跑，用于确认实现与口径）
export M17_EVAL_RUN=true M17_EVAL_SPLIT=dev
./mvnw -s maven-settings.xml -Dtest=M17RecommendEvaluation test

# 4. 独立测试集（按规范只能跑一次；重跑会使本次评测作废）
export M17_EVAL_RUN=true M17_EVAL_SPLIT=test
./mvnw -s maven-settings.xml -Dtest=M17RecommendEvaluation test
```

评测结果同时写入 `ai_recommend_log`（`experiment_tag` = `RECOMMEND` / `BASELINE_HOT`），
可按批次分组复核。
