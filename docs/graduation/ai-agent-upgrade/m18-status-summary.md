## 一、项目是什么

- **BitForum**：个人毕业设计项目，Java 后端 + React 前端的社区论坛。
- 第一阶段 M1-M12 已完成并合入 `main`：注册登录、JWT/BCrypt、板块、文章草稿-待审-发布-驳回-下架状态机、
  评论、点赞热榜、收藏搜索、通知中心、举报治理、管理员看板、用户主页、关注、文件上传、
  Swagger/OpenAPI、Redis 指标定时落库、Actuator 健康检查。
- 第二阶段 M13-M18 把它升级为「**基于 Spring Boot + React 的多智能体智能社区平台**」，
  六个模块**已全部完成**（本文件主要讲这一段）。
- 文档一致性：README、外部 AI 简报、顶层总览/进度、项目历史总结与本节已在收尾时统一同步（此前 README 与简报还停留在 M12/M15 状态）。
- 规模：主代码 **181 个 Java 文件**（其中 AI 域 75 个）、测试代码 85 个文件；
  前端 React 19 + Vite 7，无状态管理库、无 UI 组件库、无图表库（刻意保持依赖最小）。

## 二、M13-M18 做了什么

| 模块 | 内容 | 关键实现选择 |
| --- | --- | --- |
| **M13** 基础设施与对话骨架 | Spring AI 1.1.8 + DeepSeek；V13 会话/消息表；`AgentOrchestrator` 路由；自定义 `MysqlChatMemoryRepository`；全局 AI 助手面板 | 自研轻量 Supervisor，不引 LangChain4j；**全链路降级**（AI 挂了论坛照常用） |
| **M14** 工具集 | 12 个 `@Tool` 工具（文章查询 5 + 互动写操作 7）；`ToolRegistry` 按 Agent 装配（审核/运营不给写工具） | 用户身份由 `ToolContext` 注入，**绝不由模型传**（模型会要 id、会传错） |
| **M15** RAG 知识库 | 本地 ONNX 嵌入（bge-base-zh-v1.5，768 维，离线零费用）；Redis Stack（RediSearch）向量检索；回答带可点击引用；MQ 异步索引 + 全量重建 | 只有 PUBLISHED 文章入库；内容指纹未变则跳过重新嵌入；`@ConditionalOnBean` 不可靠 → 自声明 bean |
| **M16** 内容审核 Agent | 五维风险（有害/广告/诈骗/灌水/敏感）固定字段结构化输出；决策与动作解耦；人工反馈闭环；管理台审核页 | **只自动放行、绝不自动驳回**；自动放行阈值在独立测试集覆盖率为 0 → **保持关闭** |
| **M17** 运营分析 + 推荐 | AnalystAgent 异步生成洞察（管理员触发）；三路召回（向量/热度/关注）+ RRF 融合 + Top-N；LLM 只写推荐理由 | **排序完全由 Java 完成、可复现**，模型碰不到文章 id；评测用合成数据 + 留一法 |
| **M18** 可观测性与工程化闭环 | V18 执行轨迹（路由→检索→工具调用链→每步耗时→token）；V19 用量明细（按 用户/Agent/天 + 成本估算）；`AiDegradeGuard` 统一降级；管理端执行轨迹页；**克制版预算闸门**（单用户每日上限 + 超限统一降级 + 单次输入输出保护） | 轨迹**单表 + steps JSON**；异步链路用 MQ 消息头传 traceId；工具链靠包装 `ToolCallback` 采集；预算**不新增表**（聚合 `ai_usage_stat`） |

**M18 明确砍掉的范围**（避免"功能越堆越多"）：LLM-as-Judge 评估脚本、Prompt 动态管理表、管理员 AI 设置页。
`TokenBudgetGuard` 已按**克制版**补齐（只做三件事，不做套餐/充值/会员等级/分布式配额）。

## 四、验证证据（区分"测试"与"真实调用"）

**真实 DeepSeek 调用**（非 mock，按需执行、默认跳过）：

| 场景 | 实测数据 |

| 工具调用 | 一次提问触发 2 个工具；`currentServerTime` 3ms、`searchArticles` 1ms；token 946/110/1056 |
| RAG 回答 | 回答带可点击文章引用，来源是向量检索命中片段 |
| AI 审核 | 8 条样本 8/8 成功，五维分与档位合法 |

| 推荐理由 | 5/5 条理由生成成功 |
| **执行轨迹（M18）** | 真实环境一次 AI 助手提问：轨迹 **5 步**（ROUTE→RETRIEVE→TOOL_CALL→LLM_CALL→PERSIST）、**7085 tokens**、估算 **0.0178 元** |

**关键前置验证（都是先验后写，避免"看起来做了其实是空"）**：

- T7：让模型返回**变长列表**时元素数量不稳定（4/5/6 个都出现过）→ M16 改用固定字段；
- T12：Spring AI 的工具执行循环在 provider 内部，**业务可见的最终响应里没有工具链** → 轨迹只能靠包装 `ToolCallback` 采集；
- T13：ThreadLocal **不包装就传不进线程池**（实测为 null）→ 异步链路显式传 traceId（MQ 消息头 / 任务闭包）。

## 五、效果指标与诚实边界（**必须成对出现**）

**内容审核**（开发集 70 条 + 独立测试集 30 条，人工标注）：漏放率 0%、误伤率 0%、安全召回率 100%，
严格准确率 96.7%~97.1%。自动放行阈值在测试集覆盖率 0%（说明该阈值过拟合开发集）→ 保持关闭。

**智能推荐**（合成数据 + 留一法）：融合 `HitRate@10` = **0.8889**（测试集）/ 0.8095（开发集），
纯热榜基线 0.2222 / 0.2381，随机 0.3333 / 0.2857。

三条局限（已在评测报告里写明，答辩必须主动说）：

1. 测试集只有 **9 位用户**（开发集 21 位），指标粒度粗，单个用户排名变化就会明显影响结果；
2. 文章、用户、收藏行为**全部由作者合成**，不是真实社区流量；
3. 热榜基线被刻意设成与主题无关、"关注=同兴趣"是直接设定的 ——
   因此"融合大幅超越热榜"里有**一部分是数据构造的功劳**。

另外：向量召回的区分度偏弱（同主题 vs 跨主题文章的平均相似度只差 **0.0147**，目标 0.05），
已在 M17 决策为"接受为已知局限"，**不通过改语料/换模型/调算法去凑指标**。

## 七、答辩时可用的三条"不吹"表述

1. 功能规模：**四个 Agent + 12 个工具 + RAG + 审核 + 推荐 + 可观测性**，全部有真实调用验证；
2. 工程严谨性：先做前置技术验证（T7/T12/T13）再写业务代码；每个模块跑全量测试；
   所有 AI 能力都有降级路径；轨迹、用量、降级原因可查；
3. 诚实边界：推荐指标来自合成数据（测试集 9 人）、审核阈值未达标故未启用、
   预算只做了克制版（单用户每日上限，无套餐/充值/多租户配额）。

**绝不能宣称**：exactly-once/消息绝对不丢、真实并发或生产流量、推荐指标代表真实社区效果、
已具备生产级多租户配额体系（只有单用户每日上限的克制版预算）、
已用 Elasticsearch/WebSocket/微服务/K8s/CI-CD。
