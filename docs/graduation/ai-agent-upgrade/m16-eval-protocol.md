# M16 内容审核评测规范 v1（冻结）

> **冻结日期**：2026-09-19
> **冻结含义**：本文件定义的「社区内容规则、Gold Label 标注口径、指标公式、数据集边界、阈值流程」
> 在测试集评测完成之前**不得修改**。
> 任何修改都必须先写入第七节「变更记录」并升版本号，且修改后必须重新在开发集上重跑全部指标。
> **禁止在看过测试集结果之后回头修改规则或标注** —— 那会让评测数据失去说服力。

---

## 一、为什么要冻结

M16 的评测要回答"AI 审核准不准"。如果每调整一次提示词就顺手改一下"什么算对"，
最终数字既无法比较也无法复现。因此先把**球门**钉死：

- **规则（本规范）= 球门**：定义了"什么算违规、什么算正常、模糊怎么处理"；
- **提示词与模型 = 实现**：为对齐球门而修改提示词是允许的；
  为迁就模型而放宽球门是**不允许**的（除非走变更流程并说明理由）。

## 二、社区内容规则 v1（Gold Label 的唯一判据来源）

### 2.1 五类风险维度

| 维度 | 含义 |
| --- | --- |
| `harmful` | 人身攻击、侮辱、歧视、暴力威胁 |
| `promotion` | 广告营销与站外引流 |
| `fraud` | 诈骗与钓鱼 |
| `spam` | 内容型垃圾（重复刷屏、纯乱码） |
| `sensitive` | 涉政敏感、违法违规、隐私泄露 |

### 2.2 三档判定的判定顺序

标注时**按顺序**执行，先命中先定档：

1. 命中 §2.3「明确违规清单」任一条 → **REJECT**
2. 否则命中 §2.4「明确不违规清单」任一条 → **PASS**
3. 否则 → **REVIEW**

### 2.3 明确违规清单（→ REJECT）

| 编号 | 维度 | 判据 |
| --- | --- | --- |
| H-1 | harmful | 人身攻击、侮辱性称呼（指向**人**而非观点） |
| H-2 | harmful | 地域 / 性别 / 职业 / 身份歧视 |
| H-3 | harmful | 暴力威胁或煽动 |
| P-1 | promotion | 含联系方式（微信 / QQ / 手机号）的营销导流 |
| P-2 | promotion | 以利益诱饵拉人（免费领资料、返利、内部名额、限时优惠） |
| F-1 | fraud | 索取账号密码、银行卡、身份证等敏感信息 |
| F-2 | fraud | 虚假中奖、虚假补贴、假冒官方活动 |
| F-3 | fraud | 投资 / 收益承诺（"稳赚""包回本"） |
| S-1 | spam | **明显重复**：同一内容重复 ≥ 3 次，或连续重复字符 ≥ 8 个 |
| S-2 | spam | **纯乱码 / 无意义符号串**：无任何可读语义的字符组合 |
| X-1 | sensitive | 泄露他人隐私（手机号、住址、身份证、工作单位） |
| X-2 | sensitive | 寻求或传授违法违规方法（绕过实名、刷单、外挂等） |

### 2.4 明确不违规清单（→ PASS）

| 编号 | 判据 |
| --- | --- |
| N-1 | 正常技术讨论、提问、经验分享、复盘 |
| N-2 | 观点性负面评价（"这个方案不行 / 压测数据有问题"）—— 指向**观点**而非人身 |
| N-3 | **单个短互动**（"顶一下""感谢分享""学到了"）—— 单次不构成 spam |
| N-4 | 与主题无关但不违规的日常闲聊 |
| N-5 | 推荐自己或他人的开源项目 / 文章，**不含联系方式与利益诱饵**（例如只说"欢迎试用提 issue"） |

> **N-3 与 S-1 的边界**：单个短互动不算违规；只有**重复达到 §2.3 S-1 阈值**才判 REJECT。
> **N-2 与 H-1 的边界**：可以否定观点、否定方案，不能否定人。

### 2.5 边界情况（→ REVIEW）

| 编号 | 判据 |
| --- | --- |
| B-1 | 语义模糊的引流：暗示"资料在我主页"但无链接、无联系方式、无利益诱饵 |
| B-2 | 含站外链接但内容本身有技术价值，是否属营销需人工判断 |
| B-3 | 影射式表达：暗示敏感或规避审核，但未展开、无明确违规内容 |
| B-4 | 疑似诈骗 / 广告但证据不足（话术接近但缺少关键特征） |

### 2.6 明确不属于 M16 范围

- **行为型刷屏**（短时间高频发布、多账号协同）—— 属于风控与限流，不是内容审核；
- **图片 / 视频 / 音频内容** —— M16 只处理文本；
- **作者历史行为**（屡次违规、信用分）—— 不在本模块输入范围内。

判断时**只看本条内容本身**，不得引入作者历史或上下文臆测。

## 三、Gold Label 标注规则

1. 每条样本必须写明 `labelReason`，并**引用本规范的具体条款编号**（如「P-1 含微信号」）；
2. 标注时**先不看模型输出**，避免锚定到模型判断；
3. 标注完成后，若某条无法用现有条款覆盖，**先补充条款再标注**，不允许"凭感觉"；
4. 边界样本必须写明为何落在 REVIEW 而非相邻档位；
5. 单人标注的补偿措施：每条都留下条款引用，使标注**可复核、可重放**。

## 四、指标公式

### 4.1 一级指标（安全，主指标 —— 决定能否上线）

设：
- `R` = 标注为 REJECT 的样本集合
- `P` = 标注为 PASS 的样本集合
- `pred(x)` = 模型对该样本的判断

| 指标 | 公式 | 含义 |
| --- | --- | --- |
| **漏放率** | `#{x∈R, pred=PASS} / #R` | 违规内容被当成正常内容（最危险） |
| **误伤率** | `#{x∈P, pred=REJECT} / #P` | 正常内容被拒绝（体验损失） |
| **安全召回率** | `#{x∈R, pred∈{REJECT,REVIEW}} / #R` | 违规内容未被"放过"（REVIEW 由人工兜底） |

### 4.2 二级指标（质量，参考 —— 用于横向比较与迭代方向）

| 指标 | 公式 |
| --- | --- |
| 严格三分类准确率 | `#{pred(x) == label(x)} / N` |
| REJECT 精确率 | `#{x∈R, pred=REJECT} / #{pred=REJECT}` |
| REJECT 召回率 | `#{x∈R, pred=REJECT} / #R` |

### 4.3 必报的分布（避免只报总数掩盖结构）

- **REVIEW 样本的落点分布**：标注为 REVIEW 的样本，模型判成 PASS / REVIEW / REJECT 各多少条；
- **五类维度的混淆矩阵**（harmful / promotion / fraud / spam / sensitive 各自的判对情况）。

### 4.4 硬约束（不达标即视为不合格）

1. **漏放率必须 = 0**；
2. 允许自动放行的样本中**不得包含任何 label ≠ PASS 的样本**（见第六节）。

## 五、数据集边界

| 集合 | 目标条数 | 用途 | 使用规则 |
| --- | --- | --- | --- |
| **开发集** | 70 | 调提示词、扫阈值、迭代 | 可反复使用 |
| **测试集** | 30 | 只产出最终指标 | **冻结阈值后才可使用，且只用一次** |
| （当前）开发集 | 20（待扩） | 流程验证 | 本轮已跑，规范生效后按 v1 重新标注 |

**规则**：

1. 两个集合按类别**分层抽样**，保证五类风险 + 正常内容的分布近似；
2. 测试集在阈值冻结前**不得查看模型输出**（连单条结果也不看）；
3. 禁止用测试集结果反过来调提示词；若确需调整，则**测试集作废并重新构造**；
4. 样本进入集合后，修改标注必须记入第七节变更记录；
5. 测试集样本单独存放（`moderation-test-samples.json`），开发集为 `moderation-dev-samples.json`。

## 六、自动放行阈值的确定流程

自动放行是 M16 中**唯一会自动改变线上状态**的动作，因此阈值必须由数据确定、而非预设。

1. 在**开发集**上跑评测，记录每条样本的 `(decision, confidence, riskScore, label)`；
2. **阈值扫描**：在候选网格上枚举 `(confidenceThreshold, maxRisk)`，
   例如 confidence ∈ {0.80, 0.85, 0.90, 0.95, 0.99}、maxRisk ∈ {0.01, 0.05, 0.10, 0.20, 0.30}；
3. 对每组阈值计算：若按此阈值自动放行（条件：`decision=PASS` 且 `confidence ≥ 阈值` 且 `riskScore < maxRisk`），
   被放行的样本集合；
4. **筛选条件**：该集合中**不得出现任何 `label ≠ PASS` 的样本**（零非 PASS 放行）；
5. 在满足条件的所有组合中，选**覆盖率最高**（放行样本数最多）的那组；
6. **冻结**阈值，写入 `application.yml` 并在变更记录中登记；
7. 在**测试集**上验证：漏放率 = 0、误伤率 = 0，且自动放行覆盖率不低于开发集水平；
8. 若测试集不达标 → 允许回到步骤 2 重新扫描，但**必须记录为一次阈值迭代**；
   **不得修改规则或标注**。

> 注：开发集只有 20 条时无法做有意义的阈值扫描（正常样本仅 7 条）；
> 因此阈值确定必须等到开发集扩充到目标规模之后。

| 迭代 | 开发集扫描结果 | 测试集验证 | 判定 |
| --- | --- | --- | --- |

**迭代 #1 未通过的分析**：开发集上恰好有 4 条 `confidence=0.99 且 risk=0.00` 的样本，
测试集上一条都没有 —— 说明该阈值是**过拟合开发集**的产物，而不是稳定的决策边界。
按规范 §6 步骤 8，允许重扫阈值，但**禁止使用测试集结果回改**；
而开发集数据未变，重扫只会得到同一结果，因此**不再迭代**，结论是：**样本量不足以稳定估计阈值**。

**由此得出的结论**：`auto-approve-enabled` **保持默认关闭**。这不是"保守起见"，
而是数据不支持启用一个会自动改变线上状态的动作 —— 这一点在报告与配置注释中均已如实记录。

**已跑结果的状态**：规范生效前跑过一次 20 条开发集评测（严格准确率 85%、漏放 0%）。
该结果**基于旧标注口径**（`dev-014` / `dev-015` 当时标为 REVIEW），
按 v1 已重新标注并重跑，旧结果仅作流程验证记录保留，不作为评测结论。
