## 必背 12 问速记版

这一节是面试前优先背的短版。先把这 12 个问题讲顺，再去看后面的长版八股。

### 1. 介绍一下你的论坛项目。

我做的是一个基于 Spring Boot 3 + MyBatis-Plus 的轻量级论坛系统，功能包括用户注册登录、文章发布、评论、Redis 浏览量和点赞、Redis ZSet 热门排行、RabbitMQ 异步通知，以及 Docker Compose 部署。

后续我重点做了项目质量补强：注册接口不返回密码哈希、JWT 密钥外置、异常信息不直接暴露、浏览点赞评论前校验文章存在、删除文章清理评论和 Redis、补 Flyway 初始化脚本、Docker 多阶段构建、核心测试，以及 RabbitMQ 的 Confirm/Returns、手动 ACK、幂等消费和 DLQ。

### 2. 登录认证怎么做？

注册时使用 BCrypt 对密码做哈希后存入 MySQL。登录时根据用户名查用户，再用 `matches` 校验明文密码和数据库哈希是否匹配。

登录成功后生成 JWT 返回给前端。前端后续请求写接口时带 `Authorization: Bearer <token>`。`LoginInterceptor` 解析 token，校验通过后把 `userId` 放到 request attribute，Controller 直接使用当前登录用户身份，不让前端手动传 userId。

### 3. JWT 安全吗？Payload 能不能被看到？

JWT 的 Payload 可以被 Base64 解码看到，所以 JWT 不是加密，只是签名防篡改。

因此 Payload 里不能放密码、密码哈希、手机号这类敏感信息。我项目里主要放 `userId` 和过期时间。JWT 密钥也不能硬编码，所以我把密钥改成从 `application.yml` 配置读取。

### 4. BCrypt 为什么每次哈希结果不同？

BCrypt 会自动加入随机盐，所以同一个密码每次生成的哈希结果都不同。

验证时不用自己保存盐，BCrypt 的哈希结果里已经包含盐和算法参数，`matches` 会自动取出盐再验证。

### 5. 为什么注册接口不直接返回 User？

`User` 是数据库实体，里面有 password 字段。即使 password 存的是 BCrypt 哈希，也属于敏感信息，不应该返回给前端。

所以我新增了 `UserResponse` DTO，注册接口只返回用户 id、用户名、头像等前端需要的信息。这样既避免敏感信息泄露，也让接口返回结构和数据库表结构解耦。

### 6. 浏览、点赞、评论为什么要先校验文章存在？

如果不校验文章存在，就可能对不存在的文章增加浏览量、点赞集合或评论，造成 MySQL 和 Redis 里出现脏数据。

我后来把浏览、点赞、取消点赞、评论发布这些入口都加了文章存在校验。文章不存在就直接返回失败，不再写 Redis 或 comment 表。

### 7. 点赞为什么用 Redis Set？

点赞业务要求同一个用户对同一篇文章只能点赞一次。Redis Set 天然去重，适合存某篇文章被哪些用户点过赞。

我用类似 `article:{id}:likes` 的 key 存点赞用户 id。点赞时加入 Set，取消点赞时移除，统计点赞数时看 Set 大小。

### 8. 热门排行为什么用 Redis ZSet？

热门排行需要按分数排序，Redis ZSet 正好是“成员 + 分数”的结构，适合做 Top N 排行。

我把文章 id 作为 member，热度作为 score。浏览文章时热度 +1，点赞时热度 +3，热门接口直接从 ZSet 取前 10 名，不再遍历 MySQL 全量文章计算。

### 9. 为什么用 RabbitMQ，不直接用线程池？

线程池只能在当前进程内异步执行，服务重启时未处理任务可能丢失，也不方便后续拆服务。

RabbitMQ 是独立消息中间件，可以把文章发布主流程和通知逻辑解耦。文章保存成功后发送消息，消费者异步处理通知。后续如果通知逻辑变复杂，也不用影响发布文章的主流程。

### 10. RabbitMQ 怎么保证消息可靠？

我从生产者和消费者两边做了增强。

生产者开启 ConfirmCallback，判断消息是否到达 Broker；开启 ReturnsCallback 和 mandatory，判断消息是否成功路由到队列。

消费者使用手动 ACK，处理成功才 `basicAck`；处理失败时 `basicNack(requeue=false)`，失败消息进入 DLQ。消息体里带 `messageId`，消费者用 Redis Set 记录已处理消息，避免重复消费。

### 11. Docker 在项目里怎么用？

我使用 Docker 多阶段构建后端镜像。builder 阶段用 Maven 镜像从源码打包，runtime 阶段用 JRE 镜像运行 jar。

然后用 Docker Compose 编排 MySQL、Redis、RabbitMQ 和 Spring Boot app。后端容器通过服务名访问其他容器，比如 `mysql:3306`、`redis:6379`、`rabbitmq:5672`。宿主机访问 MySQL 用 `3307`，避免和本机 MySQL 的 `3306` 冲突。

### 12. 你补了哪些测试？为什么这些测试重要？

我补的测试主要覆盖容易出错、也容易被追问的核心规则，包括注册登录参数校验、发布文章发送 MQ、Redis 点赞去重、热门排行、非作者删除失败、评论不存在文章失败、RabbitMQ 重复消息 ACK。

这些测试不是为了堆数量，而是证明关键业务规则真的被验证过。比如同一用户重复点赞不能重复计数，非作者不能删除文章，评论不能发到不存在的文章下。

## 1. 项目介绍

### Q1：介绍一下你的论坛项目。

答：

我做了一个基于 Spring Boot 3 + MyBatis-Plus 的轻量级论坛系统，主要功能包括用户注册登录、JWT 认证、文章发布、评论、Redis 浏览量和点赞、热门排行、RabbitMQ 异步通知，以及 Docker Compose 部署。

这个项目一开始是基础论坛功能，后面我重点围绕安全性、数据一致性、部署可信度和测试覆盖做了补强。比如注册接口不返回密码哈希，JWT 密钥改成配置外置，浏览、点赞、评论前校验文章是否存在，删除文章时清理评论和 Redis 数据，用 Flyway 管理数据库初始化，用 Docker 多阶段构建实现更可靠的一键启动。

### Q2：这个项目和岗位要求有什么匹配点？

答：

岗位要求 Java、Spring Boot、MySQL、MyBatis、Redis、Docker 和联调排查能力，我的项目都有对应实践。

Spring Boot 负责后端接口，MyBatis-Plus 负责数据库访问，MySQL 存用户、文章和评论，Redis 做浏览量、点赞和热榜，RabbitMQ 做文章发布后的异步通知，Docker Compose 编排 MySQL、Redis、RabbitMQ 和后端服务。

另外岗位提到安全和质量问题，我也专门修过注册接口泄露密码哈希、JWT 密钥硬编码、不存在文章仍能点赞评论、删除文章后关联数据不清理等问题。

## 2. Spring Boot 基础

### Q3：Spring Boot 和 Spring 有什么区别？

答：

Spring 是 Java 后端开发的基础框架，核心是 IOC 和 AOP。Spring Boot 是基于 Spring 的快速开发框架，主要解决配置繁琐、依赖整合复杂的问题。

Spring Boot 提供自动配置、内嵌 Tomcat、starter 依赖和 application.yml 配置，让项目可以更快启动。

我的项目就是 Spring Boot 项目，Controller、Service、Mapper、Redis、RabbitMQ、JWT 配置都交给 Spring Boot 管理。

### Q4：IOC 是什么？

答：

IOC 是控制反转，意思是对象的创建和依赖关系不再由我们手动 new，而是交给 Spring 容器管理。

比如我的 RedisService、ArticleService、UserService 都加了 @Service，Spring 启动时会创建这些 Bean。Controller 里通过 @Autowired 注入 Service，不需要自己 new。

这样可以降低类之间的耦合，也方便测试和统一管理。

### Q5：@Controller 和 @RestController 有什么区别？

答：

@Controller 通常用于返回页面，适合传统 MVC。

@RestController 等于 @Controller + @ResponseBody，方法返回值会直接序列化成 JSON，适合前后端分离接口。

我的项目是 REST API，所以 UserController、ArticleController、CommentController 都使用 @RestController。

### Q6：@Service、@Component、@Configuration 分别干嘛？

答：

@Component 是通用组件注解，表示这个类交给 Spring 管理。

@Service 通常标在业务逻辑类上，比如 UserService、ArticleService、RedisService。

@Configuration 表示配置类，比如 WebMvcConfig，用来注册登录拦截器。

这些注解本质上都会让类成为 Spring Bean，只是语义不同，方便分层和阅读。

### Q7：Interceptor 和 Filter 有什么区别？

答：

Filter 是 Servlet 规范的一部分，作用范围更底层，会在请求进入 Servlet 前后处理。

Interceptor 是 Spring MVC 提供的拦截器，作用在 Controller 调用前后，更适合做登录校验、权限校验等和业务接口相关的逻辑。

我的项目用 LoginInterceptor 做登录拦截，拦截发布文章、点赞、评论等需要登录的接口，从请求头中解析 JWT，拿到 userId 后放到 request attribute 里。

## 3. 登录认证与安全

### Q8：你的登录认证怎么做的？

答：

用户注册时，后端用 BCryptPasswordEncoder 对密码做哈希后存入 MySQL。登录时，根据用户名查用户，再用 encoder.matches 校验明文密码和数据库里的哈希值是否匹配。

登录成功后，用 JwtUtil 生成 JWT token 返回给前端。前端后续请求需要登录的接口时，在请求头里带上 token。LoginInterceptor 会解析 token，校验通过后把 userId 放入 request attribute，Controller 就能知道当前登录用户是谁。

### Q9：JWT 是什么？由哪几部分组成？

答：

JWT 是一种无状态登录令牌，通常由三部分组成：

```text
Header.Payload.Signature
```

Header 表示签名算法，Payload 存放用户 ID、过期时间等声明，Signature 是用密钥对前两部分做签名。

我的项目里 JWT 主要存 userId 和过期时间，用来识别当前登录用户。

### Q10：JWT 安全吗？Payload 能不能被看到？

答：

JWT 的 Payload 可以被 Base64 解码看到，所以 JWT 不是加密，只是签名。

因此 Payload 里不能放密码、密码哈希、手机号这类敏感信息。JWT 的安全性主要依赖签名密钥、过期时间和 HTTPS 传输。

如果有人篡改 Payload，比如把 userId 改成别人的，签名校验会失败，后端应该拒绝这个 token。

### Q11：JWT 密钥为什么不能硬编码？

答：

JWT 密钥如果硬编码在代码里，代码泄露后密钥也会泄露，别人就可能伪造 token。

我项目里一开始 JwtUtil 有硬编码密钥，后来改成 JwtProperties，从 application.yml 读取配置。这样代码和配置分离，后续上线时也可以通过环境变量或配置文件替换密钥。

### Q12：为什么注册接口不能返回 User 实体？

答：

User 实体里包含 password 字段，虽然存的是 BCrypt 哈希，不是明文，但哈希也属于敏感信息，不应该返回给前端。

我后来新增了 UserResponse DTO，注册成功后只返回 id、username 等必要字段，不返回 password。

这个改动体现的是接口安全意识：数据库实体不一定等于接口响应对象。

### Q13：DTO 是什么？为什么要用 DTO？

答：

DTO 是 Data Transfer Object，数据传输对象，用来定义接口输入或输出的数据结构。

使用 DTO 的好处是可以隔离数据库实体和接口返回，避免把不该暴露的字段返回给前端，也能让接口结构更稳定。

我的项目里 UserResponse 就是 DTO，用于注册接口返回用户信息，避免直接返回 User 实体导致密码哈希泄露。

### Q14：BCrypt 为什么每次加密结果不同？

答：

严格说 BCrypt 不是加密，而是密码哈希算法。

BCrypt 每次生成哈希时都会自动加入随机盐，所以同一个密码每次生成的哈希结果不同。

登录时不能简单地把明文密码重新哈希后字符串比较，而是要用 encoder.matches(明文密码, 数据库哈希值) 校验。

## 4. 异常处理与接口质量

### Q15：为什么不能直接返回 e.getMessage()？

答：

e.getMessage() 可能包含数据库错误、SQL 信息、内部类名、文件路径等敏感信息。如果直接返回给前端，会有安全风险，也会让接口响应不统一。

我项目里改了 GlobalExceptionHandler：服务端用 log.error 记录详细异常，客户端只返回统一错误提示。这样既方便排查，也避免泄露内部实现。

### Q16：为什么要统一返回 Result？

答：

统一返回 Result 可以让前端稳定处理响应格式，比如统一包含 code、message、data。

如果每个接口返回格式都不一样，前端联调成本会高，也不利于排查问题。

我的项目 Controller 基本都返回 Result，例如 Result.ok 和 Result.fail。

### Q17：@Valid 是干嘛的？

答：

@Valid 用于触发参数校验，通常配合实体或 DTO 字段上的 @NotBlank、@Size、@NotNull 等注解使用。

比如发布文章时，可以要求 title 和 content 不能为空。如果参数不合法，后端应该直接返回错误，不进入业务逻辑。

我的项目已经在部分接口上使用 @Valid，后续还可以继续补全 DTO 和参数校验。

## 5. MySQL 与事务

### Q18：MySQL 索引是什么？为什么能加速查询？

答：

索引是数据库为了加快查询建立的数据结构。MySQL InnoDB 常用 B+ 树索引。

没有索引时，数据库可能要全表扫描。有索引时，可以通过树结构快速定位数据，减少扫描行数。

我的项目中 user_info 可以对 username 建唯一索引，article 可以对 user_id 建索引，comment 可以对 article_id 建索引，方便按用户查文章、按文章查评论。

### Q19：索引什么时候会失效？

答：

常见情况包括：

```text
对索引列使用函数
like 以 % 开头
隐式类型转换
or 条件使用不当
联合索引不符合最左前缀原则
查询条件区分度太低，优化器认为全表扫描更划算
```

比如 username 是字符串，但查询时不加引号，可能发生隐式类型转换，影响索引使用。

### Q20：事务 ACID 是什么？

答：

ACID 是事务的四个特性：

```text
原子性：事务里的操作要么都成功，要么都失败
一致性：事务前后数据要保持正确状态
隔离性：多个事务之间互不干扰
持久性：事务提交后数据要持久保存
```

我的项目删除文章时，要删除评论、删除文章、清理 Redis。数据库部分的删除评论和删除文章应该在一个事务里，避免文章删了但评论还在。

### Q21：@Transactional 是干嘛的？

答：

@Transactional 用来开启事务。方法执行成功时提交事务，出现运行时异常时回滚事务。

我的 ArticleService.delete 加了 @Transactional，因为删除文章不是单一操作，而是一个业务流程：先删评论，再删文章，最后清理 Redis。

需要注意，Redis 不在 MySQL 事务里，所以 Redis 清理失败不能自动让 MySQL 回滚。更严谨的做法可以记录补偿任务或重试。

### Q22：事务失效的常见场景有哪些？

答：

常见场景：

```text
方法不是 public
同一个类内部方法自调用
异常被 catch 后没有继续抛出
抛出的是受检异常但没有配置 rollbackFor
类没有被 Spring 管理
数据库表不支持事务
```

我的项目里事务加在 Service 层的 public 方法上，这样比较符合 Spring 事务的使用方式。

## 6. MyBatis / MyBatis-Plus

### Q23：MyBatis 是什么？

答：

MyBatis 是持久层框架，用来把 Java 方法和 SQL 执行绑定起来，简化 JDBC 操作。

MyBatis-Plus 是 MyBatis 的增强工具，提供 BaseMapper、条件构造器等能力，可以减少基础 CRUD 代码。

我的项目里 ArticleMapper、UserMapper、CommentMapper 继承 BaseMapper，就可以直接使用 insert、selectById、deleteById 等方法。

### Q24：#{} 和 ${} 有什么区别？

答：

#{} 是预编译参数，会使用占位符，能防止 SQL 注入。

${} 是字符串拼接，会直接把内容拼进 SQL，有 SQL 注入风险。

一般业务参数应该优先使用 #{}，只有表名、字段名这类无法预编译的场景才可能用 ${}，但必须严格校验。

### Q25：QueryWrapper 是干嘛的？

答：

QueryWrapper 是 MyBatis-Plus 提供的条件构造器，可以用 Java 代码拼查询条件，减少手写 SQL。

比如我的 UserService.register 中，用 QueryWrapper 根据 username 查重：

```text
where username = ?
```

这样比手写 SQL 更方便，也更符合 MyBatis-Plus 的用法。

## 7. Redis

### Q26：Redis 为什么快？

答：

Redis 快主要因为：

```text
数据存内存
单线程模型减少线程切换和锁竞争
使用 IO 多路复用处理大量连接
数据结构简单高效
```

我的项目用 Redis 做高频读写的数据，比如浏览量、点赞数和热榜。

### Q27：你的浏览量为什么用 Redis String？

答：

浏览量本质是一个数字计数器，Redis String 支持 increment 原子自增，非常适合做计数。

我的 key 是：

```text
article:{id}:views
```

用户浏览文章时调用 increaseViews，让浏览量加 1。

### Q28：你的点赞为什么用 Redis Set？

答：

点赞需要解决两个问题：

```text
记录哪些用户点过赞
防止同一个用户重复点赞
```

Redis Set 天然去重，所以我用：

```text
article:{id}:likes
```

把 userId 存进去。同一个 userId 添加多次，Set 里仍然只有一份，所以点赞数不会重复增加。

### Q29：热门排行为什么适合用 ZSet？

答：

ZSet 是有序集合，每个成员都有一个 score，可以按 score 排序。

热门文章排行可以把 articleId 作为成员，把浏览量、点赞数计算出来的热度值作为 score，然后用 reverseRangeWithScores 获取前 N 名。

我的项目里已经有 article:hot 这个 ZSet 设计，后续可以把热榜逻辑进一步切到 ZSet。

### Q30：Redis 和 MySQL 数据不一致怎么办？

答：

要看具体场景。

我的项目里文章主体数据在 MySQL，浏览量和点赞在 Redis。删除文章时，如果只删 MySQL，不清 Redis，就会留下脏缓存，所以我补了 deleteArticleData 清理浏览量、点赞集合和热榜数据。

更复杂的场景可以用延迟双删、消息队列补偿、定时任务对账等方式保证最终一致性。

### Q31：缓存穿透、击穿、雪崩是什么？

答：

缓存穿透：查询不存在的数据，请求一直打到数据库。解决方式有缓存空值、布隆过滤器。

缓存击穿：某个热点 key 过期，大量请求同时打到数据库。解决方式有互斥锁、热点 key 不过期、提前刷新。

缓存雪崩：大量 key 同时过期或 Redis 故障，导致请求集中打到数据库。解决方式有过期时间随机化、限流、降级、Redis 高可用。

### Q32：Redis 持久化 RDB 和 AOF 区别？

答：

RDB 是定期生成快照，恢复快，占用空间小，但可能丢失最近一段数据。

AOF 是记录写命令，数据更完整，但文件更大，恢复可能更慢。

生产环境可以根据数据重要性选择，也可以混合使用。

## 8. RabbitMQ

### Q33：为什么用 RabbitMQ，不直接用线程池？

答：

线程池适合单机内部异步任务，但任务还在当前应用进程里。应用重启或宕机时，内存中的任务可能丢失。

RabbitMQ 是独立消息中间件，可以削峰、解耦、支持消息持久化和消费者重试，更适合跨服务或可靠性要求更高的异步流程。

我的项目里文章发布是主流程，通知是附加流程，所以用 RabbitMQ 把它们解耦。

### Q34：RabbitMQ 的 Exchange、Queue、RoutingKey 是什么？

答：

Producer 把消息发送到 Exchange，Exchange 根据 RoutingKey 和绑定规则把消息路由到 Queue，Consumer 从 Queue 中消费消息。

我的项目目前比较简单，文章发布后向 article.publish.queue 发送消息，NotificationListener 监听这个队列。

### Q35：如何防止 RabbitMQ 消息丢失？

答：

一般从三个阶段考虑：

```text
生产者到 RabbitMQ：开启 publisher confirm
RabbitMQ 自身：队列和消息持久化
消费者处理：手动 ACK，处理成功后再确认
```

我的项目目前是基础异步通知，后续如果要提高可靠性，可以补 confirm、持久化和手动 ACK。

### Q36：如何防止重复消费？

答：

消息队列不能完全保证业务上没有重复，所以消费者要做幂等。

常见方式：

```text
用唯一业务 ID 去重
数据库唯一索引
Redis setnx 记录已处理消息
消费前查询状态
```

比如文章通知消息可以带 articleId，消费者处理前判断这个通知是否已经处理过。

## 9. Docker / 部署

### Q37：Docker 镜像和容器有什么区别？

答：

镜像是静态模板，包含运行应用需要的文件和环境。

容器是镜像运行起来后的实例。

可以理解为镜像是类，容器是对象。

我的项目用 Dockerfile 构建后端镜像，用 docker-compose.yml 启动后端、MySQL、Redis、RabbitMQ 这些容器。

### Q38：Dockerfile 多阶段构建有什么好处？

答：

多阶段构建可以把“构建环境”和“运行环境”分开。

我的第一阶段用 Maven 镜像打包项目，第二阶段用 JRE 镜像运行 jar。这样最终镜像不需要包含 Maven 和源码，体积更小，也更干净。

更重要的是，它不再依赖本机提前生成 target jar，真正做到从源码构建。

### Q39：JDK 和 JRE 有什么区别？

答：

JDK 是 Java 开发工具包，包含编译器 javac、运行环境和开发工具。

JRE 是 Java 运行环境，只负责运行已经编译好的 Java 程序。

我的 Dockerfile 第一阶段需要编译打包，所以用带 Maven 和 JDK 的镜像。第二阶段只运行 jar，所以用 JRE 镜像。

### Q40：docker-compose.yml 是干嘛的？

答：

docker-compose.yml 用来定义多个容器如何一起启动，包括镜像、端口、环境变量、数据卷、网络和依赖关系。

我的项目用 Docker Compose 同时启动 MySQL、Redis、RabbitMQ 和 Spring Boot app，方便一条命令拉起完整后端环境。

### Q41：3307:3306 是什么意思？

答：

Docker 端口映射格式是：

```text
宿主机端口:容器端口
```

3307:3306 表示我电脑访问 localhost:3307，会转发到 MySQL 容器内部的 3306。

这样做是因为我本机可能已经有 MySQL 占用了 3306，所以把宿主机端口改成 3307，避免冲突。

后端 app 容器和 mysql 容器在同一个 Compose 网络里，所以 app 仍然通过 mysql:3306 访问数据库，不需要用 3307。

### Q42：volume 是什么？

答：

volume 是 Docker 的数据卷，用来持久化容器数据。

如果 MySQL 数据只存在容器内部，容器删除后数据也会丢。使用 volume 后，MySQL 数据会保存在 Docker 管理的数据卷里，容器重建后数据仍然存在。

我的 docker-compose.yml 里 mysql-data 就是 MySQL 数据卷。

## 10. Flyway

### Q43：Flyway 是干嘛的？

答：

Flyway 是数据库结构版本管理工具，可以把建表、加字段、加索引等 SQL 脚本按版本执行。

我的项目新增了 V1__init_schema.sql，用来初始化 user_info、article、comment 三张表。

这样新环境启动时可以自动建表，不需要手动执行 SQL。

### Q44：baseline-on-migrate 是干嘛的？

答：

baseline-on-migrate 用于让 Flyway 接管一个已经有表的数据库。

如果数据库不是空的，但没有 flyway_schema_history 表，Flyway 默认会报错。开启 baseline-on-migrate 后，Flyway 会先建立历史表，并把当前数据库标记为一个基线版本。

我的本地库之前手动建过表，所以用了这个配置让 Flyway 接管旧库。

## 11. 测试与联调排查

### Q45：mvn test 是干嘛的？

答：

mvn test 会编译项目并运行测试代码，用来验证项目是否能正常启动、业务逻辑是否符合预期。

我的项目一开始只有 contextLoads 测试，只能证明 Spring 上下文能启动。后续我开始补业务测试，比如 Redis 点赞去重测试。

### Q46：单元测试和集成测试有什么区别？

答：

单元测试通常只测一个类或一个方法，依赖会用 mock 隔离，速度快。

集成测试会启动 Spring 容器，甚至连接真实数据库、Redis、RabbitMQ，更接近真实运行环境，但速度更慢。

我的 RedisServiceTest 使用 @SpringBootTest，并连接真实 Redis，所以更偏集成测试。

### Q47：你怎么验证 Redis 点赞去重？

答：

我写 RedisServiceTest，测试前先删除测试 key，避免旧数据影响结果。

然后同一个 userId 对同一个 articleId 调用两次 like，再断言 getLikeCount 返回 1，hasLiked 返回 true。测试结束后再清理 key。

这个测试验证了 Redis Set 的去重特性确实符合点赞业务规则。

### Q48：Docker 启动失败你怎么排查？

答：

我会先看容器状态：

```text
docker compose ps
```

再看日志：

```text
docker compose logs app
```

如果是端口冲突，就检查 ports 映射。比如我遇到过本机 3306 被占用，就把 MySQL 改成 3307:3306。

如果是数据库连接问题，就检查 JDBC URL、用户名密码、容器服务名和端口。我遇到过 MySQL 8 的 Public Key Retrieval is not allowed，后来在 JDBC URL 里加 allowPublicKeyRetrieval=true 解决。

如果是 RabbitMQ Connection refused，我会看后续是否重连成功。我的项目里 app 比 RabbitMQ 启动快，前面连接失败，后面 Created new connection，说明最终成功。

## 13. 高频追问速记

### Q51：为什么删除文章要清理评论和 Redis？

答：

因为文章是主数据，评论、浏览量、点赞和热榜都依赖文章。

如果只删除文章，不删除评论，会出现评论挂在不存在文章下面的脏数据。如果不清理 Redis，会留下不存在文章的浏览量、点赞和热榜数据。

所以我删除文章时同步清理评论和 Redis，保证数据一致性。

### Q52：为什么浏览、点赞、评论前要查文章是否存在？

答：

因为这些操作都依赖文章存在。

如果不校验，就可能给不存在的文章增加浏览量、点赞数，或者发布评论，造成 MySQL 和 Redis 中的数据不一致。

我后来在浏览、点赞、取消点赞和评论发布前都补了文章存在校验。

### Q53：为什么说你的项目体现了安全和质量意识？

答：

安全方面，我修了注册接口返回密码哈希、JWT 密钥硬编码、异常信息泄露这些问题。

质量方面，我修了不存在文章还能浏览点赞评论、删除文章不清理评论和 Redis、Docker 构建依赖本机 target jar 等问题。

这些不是单纯加功能，而是让项目更接近真实开发中的可维护、可部署、可排查。

### Q54：你遇到过哪些联调或部署问题？

答：
